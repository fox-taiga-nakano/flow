# Issue の本文を詳しくする（refine step）

再現の結果（repro.md・修正前のエビデンス）とコードの調査から、実装者がこの本文だけで正しく直せる Issue の本文を `issue.md` に書く。GitHub への反映（`flow issue push`）と実装者のアサインは、人の承認の後に flow が行う。

flow から届いた step の指示（`.flow/WORKFLOW.md` の `## prompt: refine`）を、このスキルより優先する。

## プロジェクトに合わせて書き換える

- **本文の型**：プロジェクトの Issue テンプレートがあれば、手順 4 の見出しをそれに合わせる
- **調べる範囲**：仕様書・設計書の置き場所、画面とコードの対応の調べ方

## 成果物（Issue ディレクトリの中）

| ファイル        | 内容                                                              |
| --------------- | ----------------------------------------------------------------- |
| `issue.orig.md` | GitHub の元の本文。最初の 1 回だけ保存し、上書きしない            |
| `issue.md`      | 新しい本文の下書き。flow の承認後に、そのまま GitHub の本文になる |

## 手順

1. **元の本文を残す**：`gh issue view <番号> --json body --jq .body` を `issue.orig.md` に保存する（既にあれば上書きしない）。
2. **再現の結果を読む**：`repro.md`、`scripts/repro.sh`、`evidence/before/` を読み、何が起きて何が期待かを確かめる。
3. **コードを調べる**：原因の箇所、同じ処理を使うほかの箇所（同じ不具合が起きる場所）、データの条件、変えてはいけない既存の動作を調べる。場所は関数名とファイルのパスで書く（行番号は変わるので書かない）。仕様が本当に曖昧な点だけを人に聞く（推奨の答えを添えて、`result: blocked` の `needs` に書く）。コードを読めば分かることは聞かない。
4. **`issue.md` を書く**：元の説明と画像は消さずに残し、次の見出しを足す。
   - **現象と期待する動作**：再現の手順と、修正前の結果（エビデンスの要点）
   - **原因**：調べた箇所と理由
   - **対応範囲**：直すもの・直さないもの
   - **実装の条件**：守る既存の動作、同じ処理を使う箇所、データの条件
   - **確認の方法**：修正後に何が OK になればよいか（repro.sh のチェックと同じ観点）
   - **懸念**：影響の大きい点、判断が必要な点
5. **書かないもの**：推測の原因を事実のように書くこと、実装の細かいコード、社内の担当者名など公開してはいけない情報。

## flow に任せること（この step ではしない）

- `flow issue push`（GitHub への反映）、実装者のアサイン、段階の変更、コミット・push
- `flow/state.json` の変更

## 終わったら

`{flow_dir}/result-refine-{attempt}.json` に、flow の仕様（SPEC 3.3）の形で結果を書く。summary には、本文の要点と、人に確かめてほしい点を 1〜3 行で書く。

```json
{
  "result": "ok",
  "summary": "原因（保存時に一覧のキャッシュを更新していない）と対応範囲を追記",
  "artifacts": ["issue.md"]
}
```

`ok` でも `issue.md` が無ければ、flow は失敗として扱う。
